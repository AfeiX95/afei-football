| **16:00-19:00** | 51 | 5,146 | **5.4%(最低)** |
| 19:00-24:00 | 51 | 4,019 | 7.3% |

**③ 标题: 必带「主队vs客队」队名对位(SEO); 36 字上限保留, 但它不是 CTR 杠杆**

模板: **`周X 编号 联赛 主队vs客队：一个反差点`**

  正确做法是**把模糊描述换掉**(旧标题把 7~10 字浪费在"客场垫底当热门"这种搜索不认的描述上), 净字数不会增加。

- 长度预算(≤36 字): 周X编号(6) + 联赛(2-4) + 队名对位(6-14) + 冒号(1) + 反差点(8-14)。
  **反差点控制在 12 字以内**; 超长时**先砍反差点, 不要砍队名**。
- 原依据"≤30 字组 CTR 5.3% vs >30 字组 8.9%"→ **修正**: 该差值是 30 篇小样本产物。
  全量: ≤30 字 6.9% / 31-36 字 7.6% / >36 字 7.4%, >36 vs ≤30 **p=0.575 不显著**。
  → **36 字上限无害但也无收益**, 保留只为避免搜索与 feed 截断。
- ⚠️ **不要再宣称标题特征能拉 CTR**: 全量复核里"队名对位"p=0.955、"含数字/赔率"p=0.336、

  标题的作用是**让内容被搜到**(SEO)与**不被截断**, 不是提 CTR。

- 同时把 §零 的赛道优先级说清: **展现由赛道决定, 标题决定的是"能不能被搜到 + 会不会被截断"**。

### 零·六、**销售时间硬约束 —— 预告稿的有效期 = min(开球时刻, 停售时刻)**(2026-09-18 用户指出后补, 重大)

**竞彩足球销售时间(官方, [中国体彩网](https://www.lottery.gov.cn/bzzx/yxgz/20191119/1143831.html) / [sporttery.cn](https://www.sporttery.cn/help/143831.html?gid=73)):**

| | 开售 | 停售 |
|---|---|---|
| **周一至周五** | 11:00 | **22:00** |
| **周六、周日** | 11:00 | **23:00** |

**由此推出的三条硬规则:**

1. **预告类稿件的有效期不是"开球时刻", 而是 `min(开球时刻, 停售时刻)`。** 深夜场(00:00~03:00 开球)的约束**全是停售时刻**, 不是开球 —— 读者买不到, 稿子就等于废了。
2. **深夜场的正确窗口 = 当天上午 10:30~12:00**(停售前 10 小时以上 + 实测展现最好的时段)。~~旧规则"深夜场=当天 20:00-22:00 发"~~ 已被**双重推翻**: ①19:00 后实测 CTR 只有 3.9% ②贴着 22:00 发没有容错, 一旦审核延迟就过期。
3. **绝不排"已开球/已停售"的稿件**。跨天写稿必须先算: 这场球在我要发的那个时刻, 读者还买不买得到?
   - ⚠️ **2026-09-18 的实例(我犯的错)**: 把两篇周四稿(002+007、其余8场)排到 9/18 发 —— 可周四 002 在 9/17 20:15 就开球了, 其余场次也在 9/18 凌晨踢完; 又把周五 011+008 的公众号版排到"明天(周六)上午" —— 但那两场在周六 02:30/03:00 开球, 周六上午读者既买不到也看完了。**两处都是"发布晚于开球", 稿子直接报废。**

**排期公式(每日必算)**:
```
最晚发布时刻 = min(开球时刻, 当日停售时刻) − 2 小时(审核/推送容错)
推荐发布时刻 = 当天 10:30~12:00(第一优先) / 13:00~15:00(当天第二篇)
```
**生产倒排**: 要赶上 10:30 发布, 则**赛程抓取与结构判读必须在前一晚或当天 9:30 前完成**(竞彩次日盘口通常前一天中午后就能拉到 —— 09-17 12:15 那次抓取已同时拿到周四+周五两天)。

### 零·七、**骨架库与硬指标**(2026-09-29 定案: "更有价值、简洁而有深度、不要每篇一个模式")

**起因**: 09-28/09-29 连续 4 篇逐槽对齐 —— 标题同式、信息卡 5 行(连「天气: 暂无公开数据」都不变)、开场抛让球盘数字、结构对照表、每场「盘口段 → 打假段 → 增量段」的三段节奏、9 个小节标题全是「队名: 短语」、收口都是「我不给方向」。读者读第二篇就能预判全文; 这既是"没新意"的来源, 也是平台 **3.28 套路化模板写作** 的头号信号。

**① 一篇一个主张(thesis)**
- 主张 = 标题里的那个反差点, 一句话。全文只服务这一句; **不服务它的段落删掉**。
- 自检: 删掉这段, 主张还成立吗? 成立就删。
- 例: 09-29 包1 的主张是「24:0 却只给 34% 赢够」; 包3 是「同级别热门给了相反答案」。

**② 六套骨架(近 5 篇不重复; 同日两篇必须不同骨架)**

| 骨架 | 结构 | 适合 |
|---|---|---|
| ①单点深挖式 | 一个反常识 → 三层证据(盘口 / 数据 / 一手事实) → 一句自我限定 | 强焦点场、落差明确的场次 |
| ②结构对照式 | 2–3 场并置, 只锁**一个变量**(线深 / 主客 / 热门强度) | 同批同形状场次 |
| ③数据先导式 | 先抛一个异常数字 → 全篇追「这个数字从哪来」 | 定价异常、市场与常理相反 |
| ④赛程密度式 | 从赛程结构切入(10 天 4 场 / 单场淘汰 vs 两回合 / 停售约束) → 轮换与取舍 | 密集期、杯赛、赛季初 |
| ⑤人物/教练式 | 换帅、首秀、纪录、核心缺阵当主线, 数据结构退成一节 | 有人物新闻的场次 |
| ⑥问答式 | 读者最可能问的 3 个问题各一段 | 大众关注高但信息杂的场次 |
| ⑦全景深挖式 | **外媒评价 / 战术风格对位 / 核心矛盾 / 近期状态** 四块并置(每块 200–300 字) | **深度单场稿(1200–1500 字)**, 用户点名的重点场次 |

- **轮换台账**: 当日 `工作日志_YYYYMMDD.md` 记每篇一行(编号 + 骨架 + 反差点)。

**③ 硬指标(替代旧的「信息卡 5 行」口径)**

| 项 | 指标 |
|---|---|
| 中文字 | **单场 800–1000 / 串烧 900–1100 / 深度单场 1200–1500**(2026-09-30 用户新增"深度单场稿"档: 用于点名重点场次, 需外媒+战术+矛盾+状态四块齐备; 旧的 800–1200 作废) |
| 全篇数字 | ⚠️ **不是"越少越好"**(2026-09-29 实测修正): 硬约束是**同一数字最多出现 2 次**(表 + 论点句); 总量按住场次控制 —— 单场 ≤20 / 双场 ≤35 / 三场 ≤55(09-29 三场稿实测 全部数字 100/97、核心 53/54, 属可接受) |

**③·五、两个夹缝约束必须同时满足(2026-09-29 回炉实测, 重要)**

- **下限**: `risk_scan` 的**纯数据句占比 ≥30%** —— 这是公告第 1 点「公开可验证的赛事技术分析占比过小」的代理指标, 低于 30% **直接判不合格**(定义: 一句里 ≥2 个数据点且 0 个结论词)。
- **上限**: 串烧 **朱雀 <2.0**(单场 <2.5); 朱雀最恨"句长均匀 + 数据点密"的段落。
- **只砍数据 → 踩破下限; 只堆数据 → 顶破上限。** 正解是**"瘦数据句"**: 每句只带 **2–3 个数字**、句中夹口语("说白了""这账看着别扭""反过来"), 并把密集数据段**拆开**; 变短要靠**去重复**(同一数字全篇只说一次), 不靠删数据。
- 09-29 回炉实测: 全部数字 130→100 / 119→97, 朱雀 2.4→**1.8** / 2.3→**1.9**, 纯数据句守在 **30% / 31%**, 中文字 932 / 1116。
- 顺带结论: 删散文(保数字)与删数据(保散文)**两头都会翻车**; 唯一稳定的方向是**减重复 + 瘦句 + 加口语**。
- ⚠️ **深度单场稿(1200–1500)更容易同时失守**(2026-09-30 周三002 实测): 外媒/战术/舆论段落天然是"叙述句 + 归因", 数据词密度低 → 首轮 **纯数据句 24%、长句 4**。**三招收口**(不改事实、不删数据): ①**并掉零数据短句**(把"场地值得单说""伤停这块是空的"这类塞进相邻句 → 分母直接下降); ②**给已有叙述补本文已核实的数字**(瘦数据句); ③**小标题带数据词** —— `risk_scan.split_sentences()` **把小标题也当句子**, 在标题里放数据词(「交锋**战绩**与让球线」「战术对位: 日本**控球**」)是零成本计分。
  → **流程: 扩写前先预留数据句额度**, 别等写完再补 —— 那时已经在撞 1500 字上限。实测收口后 **45% / 长句 0 / 朱雀 1.4 / 中文字 1444**(四道全绿)。

**④ 加三类、砍三类**
- **加**: ①**机制解释**(为什么这么定价, 而不是只说定价是多少); ②**一手事实**(赛制/场地/观众/门票/赛程密度/换帅/首发缺阵, 每条 2–3 源); ③**可迁移判据**(读者能带走的一把尺子)。
- **砍**: ①**总进球「重心」**(09-28 复盘 5 场只中 1 场, 读者拿不走); ②**近10场全陈列**(只在「这份账掺了别的口径」时才写); ③**无信息模块行**。

**⑤ 验证**
- 每篇记 3 个数(展现 / 阅读 / 读完时长), 按**骨架分组**累计; 一种骨架满 8–10 篇再比较。
- 朱雀分只当「形态合规」基线, 不当质量指标。
- ⚠️ **红线**: 我们自己的复盘账(如「重侧兑现 4/8」)**不得写进正文** —— 属战绩宣传形状。

**⑥ 收口 = 写成「结论」(2026-10-08 用户改规则: 收口要总结市场结构分析, 并给出比较看好的比分与方向)**

### Step 1：数据核查(核心步骤 — 反复犯过错，必须重视)

此步骤分两层核查，缺一不可。

**第1层：联网搜索核实基础事实**

- 用WebSearch核实：**关键球员是否还在该队**(姆巴佩2024已去皇马，克罗斯已离队)
- 用WebSearch交叉验证：首回合比分、进球者、关键数据
- ⚠️ 用户提供的文本数据可能有误，必须联网二次确认

**第2层：对照竞彩网数据逐条核对**

| 核查项 | 最容易踩的坑 |
|--------|-------------|
| 积分榜排名/积分 | 新赛制(点球胜2分)与常规算法不同 |
| 联赛总战绩 | 场次/胜/平/负必须和积分榜完全一致 |
| **主客场分开战绩** | 客场战绩最易错(神户客场写成2胜2平2负,实际3胜0平3负) |
| 近期赛果 | 区分联赛/杯赛/亚冠 |
| 历史交锋 | 最近5次比分和趋势，注意主客场 |
| 射手数据 | 进球/助攻数字 |
| 伤停信息 | 是否影响核心阵容 |
| **场均进失球数据的水分** | ⚠️ 热身赛刷分要剔除(斯图加特近10场34球=热身刷业余队,锚定正式比赛2.0; 米兰vs威尼斯升班马样本失真) |
| **官网核实(2026-09 新增)** | 主力阵容/主帅人事/夏窗转会以**官网公告**为准(inter.it / acmonza.com 等可 Playwright 无头抓取,详见 skill `club-official-site-data`); 身价需德转或雷速,官网不显 |
| **关键球员中文译名(2026-08)** | 无可靠中文译名不硬编,用"位置+原名"(如"外援前锋 Yengi") |

**核查红线(历史教训)：**
- ❌ 淘汰赛对手 ≠ 联赛阶段对手
- ⚠️ 赛制规则必查: 客场进球规则是否取消(欧足联2021-22取消)、淘汰赛只有总比分、平局→加时/点球
- ⚠️ 换帅/新帅首秀核查; 竞彩"伤停:暂无数据"≠无伤停
- ⚠️ 中立场地核查(决赛/揭幕战可能中立)
- ❌ 不编造球员纪录、不写未经数据提供的联赛表格数字
- ❌ **所有数字写进文章前再读一遍原文对照**(抄错行/看串列)
- ✅ **轮次与赛季背景核对**: 世界杯年联赛延后开赛(2026日职8月底才第4轮=正常, 不是笔误), 该背景可写进正文增加可信度

### Step 1.5：跑模型定角度(先跑模型，再定正文角度 — 2026-08-16铁律)

1. 建 config → `--model-only` 看数字
2. **模型与预设叙事冲突时以模型为准**(伯恩利vs西汉姆教训: 初稿写"客胜不稳"结果模型客胜59.6%被低估15.5点, 全文返工)
3. 判断价值看 **"Edge校准"行** — ⚠️2026-09-10 口径修正后系数≈1.0(平局×1.03/热门×1.004/冷门×0.97), **Edge校准≈裸 Edge**, 工具不再制造假 Edge; 该行仍是标准口径, 但别以为"有系数加持"就更可信
4. 方向无分歧时找"剧本差"(让球盘/净胜/大球小球的差价), 例: 拜仁场=让-2门槛、水户场=让+1低赔侧7点
5. ⚠️ **例外: 欧战强强/跨联赛档位差场景以市场为准**(2026-09-10 四场深分析三错一中的教训) — 模型吃"主队近期状态"权重过满, 而**跨联赛实力档位差是λ盲区**; 此场景λ先下调一档, 模型方向与市场冲突时**不采信模型**, 人工复核阈值从 Edge>30 降到 **±15**
6. **让球盘先看结构再写方向**(2026-09-10 全样本**469场**实测) — 竞彩让球线偏深, **让球方赢盘仅27-32% / 走水23% / 受让方不败68-77%**(让-1: 27%/23%/50%; 让+1: 32%/23%/45%); 别追"打穿"(赢盘与走水赔付不同, 不可合成单一投注项)
   - ⚠️ **2026-09-14 复盘修正: 68-77% 是"全样本基准", 不是单场方向!** 八场复盘里我在 003/007/009/012 四场都把主线写成"热门赢不够", 结果被三场主场热门零封大胜打穿(广岛6:1、弗赖堡5:0、多特3:0, 合计14:1)。
   - ✅ **工具已固化该判读**: `afei_generator.py --model-only` 现输出【让球盘结构】段(config 需带 `hhad` + `handicap_line` 字段):
     · 市场去水后的 让胜/走水/让负 三侧 + 更重的一侧与差距点数
     · **两侧差 <3 点 → 判为"无偏向"**:
       ⚠️ **2026-10-08 用户改规则后的处理**: 不再"禁止选边", 而是 **①不跟让球盘那一侧**(让球盘无偏向时它不提供方向), **②改跟胜平负/比分盘给方向与看好比分**, **③必须在收口标注这是弱读数**(例: "只差 2.5 个点、够不上偏向, 所以跟胜平负、不跟让球盘")。理由: 让球盘无偏向 ≠ 比赛无方向, 主胜 63.7% 那一侧本身就是可写的市场结论。
      · 与 469 场基准的偏离(只用于判断"比基准强/弱一档", **绝不用来反转方向**)
     · 一行"主线建议"
   - **方向规则(唯一)**: 主线**只跟市场更重的那一侧**; 基准只回答"市场定价是否异常"。写"受让方不败"前先看工具这一行。
   - ⚠️ **判读必须带让球线符号(2026-09-15 修, 坑#38)**: `hhad` 的 h/d/a 是**主队让球后**的胜平负 —— `让胜`只在**主队让球(line<0)**时等于"让球方赢够"; 主队**受让**(line>0)时 `让胜` = 主队(受让方)守住。调 `handicap_side(q, line)` 必须传线; 反例: 012 伊普斯+1 vs 阿森纳, 市场重的一侧是**阿森纳赢够(45.2% vs 30.5%)**, 不传线会印成"受让方不败"=方向说反。

**受让盘占位符速查(2026-09-04 实测坑):** `+1受让` 场景**禁用** `hcH/hcA`(会让模型概率倒挂成 2.8%/90.7% 而非 47.6%/29.1%); 改用:
- `pH2` — 重新参数化后的主队胜
- `net_neg1` — 让-1后净胜1球
- `net_neg2` — 让-1后净胜2球

完整占位符列表见 skill `afei-football-content`。

## 四、视频口播稿生成(图文→视频转换)

44. ⚠️ **`risk_scan.py` 是"子串匹配", 不看语境也不看否定 —— 三个 2026-09-18 实例**
    - **实例一(否定式误伤)**: 公众号稿写"这是它排名第 6 却**没被看好**的原因" → B 类命中 `看好`×1。词表匹配的是子串, **"没被看好"与"看好"一样触发**。改法: 换成"处在下风/不被高看"这类不含词表成分的表述。**同类高危词: 推荐/预测/方向/看好/稳 —— 写作时不能只躲正面用法, 否定式、转折式同样会命中。**
    - **实例二(markdown 与标点组合)**: 头条稿表格里写"给方向: 受让方不败" → B 类命中 `方向:`×1; 而正文小标题写 `**方向**:`(带 `**`)反而不触发。**结论: 词表里的"X:"模式只要出现"X"紧跟半角冒号就命中, 加粗符号能隔断、但不要依赖它。**

    - **实例三(扫描器"漏报"比误报更危险)**: `risk_scan.py` 的"方向"只匹配正则 `(方向|主线)[是落在]`, 所以**"失真的方向正好相反""擦的方向不一样"这类一律不报**, 可它在**项目自己的公众号禁用表里**(§五 动作2"胜负方向结论")。2026-09-18 发文风险核对时用完整禁用表复扫, 命中 **3 处**(2 处正文 + 1 处表格), 已改为"失真方式/失真之处/擦法"。**教训: 闸门脚本的覆盖范围必须与禁用表逐项对表, 否则"全绿"只是"脚本没想到"。** 完整禁用表扫描见 `.uv-cache/risk_audit_20260918.py`(硬禁词 / 术语密度 / 免责声明 / 未开售 / 比分形态 / 封号三要素), 与三道闸门配套使用。

47. ⚠️⚠️ **跨机器搬迁后必须做一次换行符/git 状态审计 —— `git status` 会说谎**(2026-09-21 实测)
    - 现象: 从 D: 搬到 X: 后 `git status` 报"干净", 但**工作区与提交并不逐字节一致**。
    - 根因两条叠加: ①拷贝来的 `.git` 里 **stat 缓存**按"大小 + mtime"信任文件未改变, 而搬迁是**字节拷贝**(大小与 mtime 都保留) → git 跳过内容比对;
      ②Git for Windows 的 **system 级 `core.autocrlf=true`** 在 `git add` 时把 CRLF 归一成 LF 存 blob, 于是工作区(CRLF)与 blob(LF)永久错位却不报错。
    - 实测规模: **343 个跟踪文件**工作区 CRLF / blob LF。**风险**: 任何 `git checkout`/`stash` 都会静默重写这些文件; 按 mtime 判断"有无改动"的校验也会失效。
    - 处理(**不动历史, 只归工作区**): ①仓库本地设 `core.autocrlf=false` + `core.eol=lf`; ②加仓库根 `.gitattributes`(`* text=auto eol=lf`);
      ③把工作区文本文件统一转 LF(blob 已是 LF, 零 churn); ④复核"CRLF 残留 = 0 且与 HEAD blob 不一致 = 0"。
    - **审计方法(可复用)**: 用 `git hash-object <file>` 与 `git rev-parse HEAD:<file>` 比 SHA —— **别用"文件里有没有 CR"当判据**: 二进制(jpg/.univer)里的孤立 CR 会骗过它(本次 4 个误报)。
    - **动作**: 任何跨机器/跨盘搬迁之后, 交付前跑一次"git 状态审计", 并把 `.gitattributes` 与 `core.autocrlf` 一起定下来。
48. ⚠️ **压字数会把三道"隐藏闸门"同时顶掉: 长句 / 朱雀 / 纯数据句占比**(2026-09-21 实测, 一次压 4 篇稿)
     - 现象: 把 4 篇稿从 1500-1800 中文字压到 1100 左右后, 原本全绿的稿子**同时**出现: ①超 60 字长句 6 个(≥2 即失败);

       (朱雀 A 项 cv 上去, 且单句 >45 字才扣分); ③**删冗余不删数据**: 优先砍同义重复的历史细节与表格单元里的长措辞,
       表格是最便宜的信息载体; ④压完**必须重跑 `gate.py` 全四道**(只跑 check_md_release 看不出朱雀与占比)。

**关键流程：**
1. 复制 match_configs 模板 → 填数据 → 跑 afei_generator
2. **出稿 → `humanizer-zh` 润色散文 → `check_structure.py <原稿> <润色稿>` 结构零漂移 → `gate.py` 四道全绿 → 发布**(字数按**中文字 800~1200**)

3. 赛后复盘 → reviews/ 归档 → 周更校准自动演进
4. 发布后后台数据 → 台账.tsv 归档 → 反哺选题/标题

**运行环境(2026-09-12 建档)：** 项目根 `运行.cmd <脚本> <参数>`(或 `run.ps1`)一键跑 —— 自动用 `.venv`(Python 3.11)并设好编码/缓存变量; 依赖清单 `requirements.txt`。⚠️ 本机 PowerShell 执行策略禁止直接运行 `.ps1`, 所以 `.cmd` 入口用 `-ExecutionPolicy Bypass` 转调。
无头抓取统一走 `采集数据/browser.py`: 它加了 **`--no-proxy-server`**(本机 Chrome/Edge 默认走系统代理, 访问 inter.it/titan007 会 ERR_CONNECTION_CLOSED), 并用 `channel='chrome'`/'msedge' **驱动本机浏览器**(playwright 自带 chromium 的下载器在本机装不上, 也不需要装); 竞彩官方 webapi 用 requests 直连会被 WAF 拦(567) → 改用 `fetch_api()` 经浏览器上下文取。
