## 一、平台实测结论（2026-10-17）

| FootyStats | ❌ 挡 | Cloudflare + 高级数据订阅墙，免费层只有聚合页 | 否 |

## 一B、三条扩源路径的实测（2026-10-17 晚上补测）

用户给了三条绕开挑战页/登录墙的思路，逐条实打实跑了一遍：

| 路径 | 站点 | 实测结果 |
|:--|:--|:--|
| ① 公开 API | API-Football（api-sports.io） | 无 key 直接 **403**；免费层每日 100 次、`/predictions` 给胜平负百分比。**已接成第三自动源**：`python scripts/ext_predict.py key --set <KEY>` 写入 `state/api-keys.json`（已 gitignore，也可用环境变量 `API_FOOTBALL_KEY`），`doctor` 会显示 key 来源；命中后记录 `provider=api-football`，`predicted_dir` + `hit_prob` + `note`（胜平负百分比 / 期望进球 / advice） |
| ① 公开 API | football-data.org | 无 token 返回 200 但正文是错误 JSON；**且 v4 没有预测端点**，只有赛程/比分 → 不是预测源 |
| ② 低防静态站 | **Sportskeeda** | ✅ **站本身没被墙**（200，无 Cloudflare），预测以「某专家预测本轮各场」的汇总文形式出现，正文格式固定：`Prediction: Everton 2-1 Chelsea`。**已接成第二自动源**。但聚合页 `/<go>/<联赛>` 常常只列出**往轮**汇总（实测抓到 GW31/32/34 的旧文），命中 2/6 场且都带 `stale_risk` |
| ② 低防静态站 | Squawka | ❌ `403 Just a moment...`（Cloudflare 盾，比 Forebet 弱不到哪去） |
| ② 低防静态站 | WhoScored | ❌ `403 Attention Required! | Cloudflare`；且 Preview 页要 matchId，得先进 livescores 页 |
| ③ 开源模型/社区均值 | GitHub 预训练权重、Superbru 社区中位数 | 本机可跑，但**训练数据截止与口径不可控**，与我们的 λ 口径无法对齐；Superbru 的 community average 需登录抓 → 暂不接 |

**落地取舍**：主力仍是 Sports Mole（逐场确定性、带首发与理由）；Sportskeeda 作**缺场兜底**（先跑 `doctor` 看该联赛有没有链接，命中必须核对是否当轮）；API-Football 留了 key 位（`API_FOOTBALL_KEY`），等用户注册后启用。

## 一C、Browser Agent 那条路怎么用（不建独立 Agent 服务）

结论是**不做端到端无人值守的 Agent 爬虫**（慢、贵、易断流，且 Forebet 类站点对 CDP 指纹也能识别）。真正可行的是「缺 1–2 场时，由当前这个 agent 现场搜一遍，喂回 `--manual`」：

```bash
# 批处理跑完发现缺场 → agent 自己搜英文媒体前瞻 → 把结论写成人工记录
python scripts/ext_predict.py --date 20261017 match 斯特拉斯 巴黎圣曼 --manual \
  --predicted "0-2" --source "Sportskeeda 摘要" --note "主队两连败，客队欧冠 4-2 胜曼城后轮换存疑"
```

理由：单场补缺只发生 1–2 次，人（或 agent）搜一次比维护一套 Agent 基础设施便宜得多；而且**格式一致性**靠 `--manual` 的固定参数保证，不会上一条引 A 站、下一条引 B 站。


## 一D、API-Football 免费层实测细节（2026-10-17 正式接入）

| 项目 | 实测 |
|:--|:--|
| 配额 | 免费层 100 次/天；本管线一场 ≈ 1 次预测 + 当天赛程 1 次（按日缓存，六场共约 7 次） |
| 赛程 | `fixtures?date=YYYY-MM-DD&timezone=Asia/Shanghai`，10-17 当日返回 **1537 场**（含 U18/U21/女足，需过滤） |
| 队名 | 与 Sports Mole 写法经常不同 → `team_aliases.json` 增加 `af` 列（`Man City`→`Manchester City`、`毕尔巴鄂`→`Athletic Club`、`巴黎`→`Paris Saint Germain`），匹配时先 `af` 后 `en` |
| 联赛过滤 | 五大联赛 id：英超 39 / 西甲 140 / 法甲 61 / 意甲 135 / 德甲 78 |
| 跨零点 | 00:30、03:00 这类北京时间属次日 → 同时查 `date` 与 `date+1`（均缓存） |
| **输出退化** | `predictions.percent` 多场都是 `10/45/45`；`predictions.goals` 返回 **`-2.5/-2.5` 坏值** → **百分比与期望进球都不能当结论引用**，只取方向 + `advice` |
| advice 形态 | `Double chance : draw or Chelsea`、`Combo Winner : Manchester City and +1.5 goals` |
| 命中率 | 本轮 **6/6 全部命中**（含 Sports Mole 只有摘要的那场） |

**结论**：AF 解决的是**覆盖率**，不是**质量**。用法定死：**只当方向参照，不把 AF 的百分比写进公开稿**；写稿仍以 Sports Mole 的比分 + 理由为主。

对照命令（顺序要紧：`report` 会整体重写报告文件，必须它先跑、`compare` 后跑）：

```bash
python scripts/ext_predict.py --date 20261017 report
python scripts/ext_predict.py --date 20261017af batch --file f.txt --provider api-football
python scripts/ext_predict.py --date 20261017 compare          # 追加「外部源互相对照」段
```

## 二、Sports Mole 抓取路径（已被脚本封装）

1. **索引页** `https://www.sportsmole.co.uk/football/predictions/`：只收录部分联赛，别指望全覆盖
2. **球队页** `https://www.sportsmole.co.uk/football/<team-slug>/`：列该队近期所有 `/preview/` 链接 —— **索引页漏掉的场次靠这里兜**
3. **预览页** 内含三样东西：`X 2-1 Y` 预测比分（§prediction-title）、双方 predicted lineups、2-6 段赛前判断
4. 中文队名 → slug 的映射在 `database/config/team_aliases.json`（`sm_slug` / `sm_alias`），新队名直接补一行即可

**坑**：①`html.unescape` 必须在灭标签**之前**，否则 `&nbsp;` 会混进比分串（曾出现 `Brentford 2-2 Liverpool &nbsp`）；②英超以外的联赛索引页常年缺行，一律走球队页兜底；③页面摘要里常混着两个队的段落开头（`Bilbao Valencia have struggled…`），引用时只取判断句。

## 四、怎么用（写作层口径）

1. **方向不一致的场次优先写**：外部说 A、模型说 B，说明这场存在结构性分歧，正好是「核心战术矛盾点」的素材
2. 引用句式：「公开赛前预报给的是 2-1」「第三方直播站的赛前判断是 0-2」——**中性、不带操作建议**
3. 外部预测与市场同侧时，用来给「市场折算」做独立旁证；与模型同侧时，用来给模型结论加一层外部支撑
4. 🔴 不写「推荐」「跟着买」「稳赢」；不把外部预测当结论，稿子里的结论仍然来自后台模型 + 市场折算的对照

## 五、脚本命令速查

```bash
python scripts/ext_predict.py key                                     # 看 key 来源 + 试连今天赛程
python scripts/ext_predict.py key --set <KEY>                         # 写入 state/api-keys.json（不入库）
python scripts/ext_predict.py doctor                                  # 体检：哪个源可用/要 key/被墙
python scripts/ext_predict.py --date 20261017 index                    # 看索引页收了哪些场次
python scripts/ext_predict.py --date 20261017 match 曼城 伊普斯         # 单场（auto：先 SM 后 SK）
python scripts/ext_predict.py --date 20261017 match 埃弗顿 切尔西 --provider sportskeeda --league 英超
python scripts/ext_predict.py --date 20261017 batch --file fixtures.txt # 批量（每行：主队 客队 [联赛]）
python scripts/ext_predict.py --date 20261017 show                      # 打印本批记录
python scripts/ext_predict.py --date 20261017 report                    # 生成 _外部预测对照.md（含三方表 + 方向不一致清单）
```

- 批量文件第三列写联赛（英超/西甲/法甲/意甲/德甲）才会走 Sportskeeda 兜底
- 记录字段 `provider`（sportsmole / sportskeeda / manual）+ `stale_risk`（Sportskeeda 汇总文是否可能是往轮，报告里标 ⚠️往轮）
- 缓存：`state/_ext_raw/`（原始 HTML，便于复核）
- 本批记录：`state/_ext_<日期>.json`
- 报告产物：`📝文章/<日期>/_外部预测对照.md`（下划线开头，是内部参照件，不进发布清单）

## 六、已知限制

1. 只有 Sports Mole 一家稳定 → 覆盖不全（本轮六场里 5 场直连命中，1 场靠球队页兜）
2. **Sportskeeda 的命中不可当轮次用**：聚合页会列出往轮汇总（实测抓到 GW31/32/34），必须核对文章里的轮次/日期；报告里已用 ⚠️往轮 标注
3. **API-Football 还差一个 key**：没有 `API_FOOTBALL_KEY` 环境变量时源不可用；注册免费层即每日 100 次（够 6–20 场/天用）
4. 摘要为英文原文，中文稿引用要自己译；只引判断句，不引赔率/让球数字
5. 预测比分与实际首发强相关，首发变（尤其轮换）时外部预测的比分会失真
6. 报告里的「后台模型」列取自 `state/_model_<日期>*.txt` 的胜平负块；**让球块不参与对照**（解析时已跳过，防覆盖）
7. Aggregated 页面的 Sportskeeda 链接排序不等于新旧顺序，别用「第一条最新」当假设
