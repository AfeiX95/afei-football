## 一、竞彩校准层: 复现校验 + 主客不对称被"平均"掉了

**做了什么**: 用户提供 2026-09-18 ~ 09-20 官方赛果 53 场(有赔率 49), 要求校正偏差。

**先立可信度**: 审计脚本在 state 快照(502 场)上**逐位复现** `calibration_state.json` 的三个桶值
(draw 1.0686→1.069 / hot 1.0153→1.015 / cold 0.8840→0.884), 证明与 `weekly_update.py` 口径等价后才下结论。

**发现 1 — 口径判决(用官方字段, 不再靠推理)**
`winFlag` 字段在 25 场"让球会改变结果"的样本里 **49/49 跟胜平负侧, 0 场跟让球侧**
→ 确认 API 的 h/d/a 是**胜平负**赔率。09-10 那次"用让球后结果配胜平负隐含"的翻车, 从此有了自动防线:
**把 `winFlag` 一并入库**, 口径再漂移会立刻暴露。

**发现 2 — `compute_coefs` 把方向性偏差平均掉了(最要紧)**
`hot_parts = [bucket_ratio(k, .40, .70) for k in "HA"]; hot_r = sum(...)/len(...)`
拆开看 502 场快照:

| 桶 | 主胜(H) | 客胜(A) | 平均 = 现行系数 |
|---|---|---|---|
| 热门 40-70% | 0.951 | 1.079 | 1.015 |
| 冷门 <30% | **0.795** | 0.973 | 0.884 |

即"热门主胜被高估 5% + 热门客胜被低估 8%"被平均成 1.015; "冷门主胜被高估 21%"被平均成 0.884。

**但 — 每个格的 95% CI 都含 1.0, 没有一个显著。** 最大的一格(冷门主胜 n=132)要判定也需约 2031 场。
**所以这不是"已确立的信号", 是"被掩盖的结构"。** 处理: 用 z² 收缩把系数拉回 1.0。

**发现 3 — state 已滞后**
库现状 560 场 vs state 502 场。差额 = 09-18 补录 18 场 + 本批净新增 40 场。
09-18 那批由 `fetch_results.py` 手工补录, **落在 `weekly_update.py` 的"最近 7 天"窗口外, 从未进过校准**。

**已应用的改动**: `calibration_state.json` → draw 1.08→**1.011**, hot 1.015→**1.001**, cold 0.89→**0.986**,
sample_size 502→**560**。⚠️ 写的是 `schema: 2`(不是 3) —— `weekly_update.py` 有
`if old.get('schema') != 2: old = {}` 的丢弃逻辑, 写错版本号会让下次 cron 静默丢掉这批校正。

**未做(需用户决定)**: `weekly_update.py` 的 `coef = 0.7*prev + 0.3*bucket` 会在下次运行时
把系数拉回(平局→1.022 / 冷门→0.969)。**改 state 只能干净一次**; 要持久必须把 z² 收缩写进 `compute_coefs()`。

## 二、头条: 用全量 262 篇推翻了 SOP §零·五 的两项半

**做了什么**: 用户给全量后台导出(2026-05-05 ~ 09-19, 262 篇, 含旧复盘点名缺的**完成率**)。

**先做转录校验**(手工转录 262 行, 必须自证):
- 点击率 = 阅读/展现: **261/262 通过**(1 行源数据自相矛盾)
- 与 9/17 旧台账交叉: **29/29 匹配, 其中 27 行 时长/点赞/评论 逐字相同**
- 行数旁证: 旧复盘记"账号累计 258 条"(9/17) → 本批 262 = 258 + 新发 4 篇 ✅

**统计纪律(本次新加)**: 展现量不是独立伯努利试验 → 组间比较用**按文章 bootstrap**, 不用二项 Wilson
(Wilson 会给出 7.0%~7.1% 这种窄到无意义的区间); 11 次比较做 **Bonferroni(阈值 0.0045)**。

**结论校正(判定只认 p 值, 不认聚合数字大小)**

| 旧结论(30篇) | 全量(262篇) | 判定 |
|---|---|---|
| 4场以上是负资产, 展现掉到不足四成 | ≥4场 展现中位 **5,970 > 单场 5,587**; CTR 差 p=0.378 | **推翻** |
| 多场稿因阅读时长短被算法压 | ≥4场 时长中位 **82 秒 = 全形态最长** | **推翻** |
| 19:00 后基本废掉 | CTR 7.3% ≈ 全站 7.4%, p=0.084 不显著; 只是展现少 | **修正** |
| 10:00-12:30 黄金 | vs 16-19时 +3.16pp, **p<0.001**(过 Bonferroni) | **确认(最强)** |
| 亚洲赛事是钱袋子 | +4.50pp, **p<0.001**(过 Bonferroni) | **确认(最强)** |
| 队名对位 CTR 11.0% | n=150 时 **p=0.955**, 完全无差异 | **推翻** |
| 含数字/赔率 CTR 更高 | n=29 时 **p=0.336**, 方向还反了 | **推翻** |
| 双场最优 | 双场-单场 p=0.024, 但三场-单场 p=0.010 一样好, **都没过 Bonferroni** | 弱确认 |

**教训: 30 篇时那些"显著"的标题特征是 n=3~5 的偶然。** 已从 SOP 撤掉"标题特征能拉 CTR"的说法。

**新发现 — 完成率不是质量指标, 是触达结构的镜子**
r(完成率, 展现)=**−0.434**、r(完成率, 粉阅占比)=**+0.585**。
完成率最低的 8 篇里 6 篇展现≥1万; 最高的 8 篇平均阅读**个位数**。
→ **完成率低往往意味着"这篇被打出去了"**, 拿它当 KPI 排稿会得出完全颠倒的结论。

## 三、标题 SEO 强化(用户要求) —— 记录一次**自我校正**

用户要求: "以后的标题尽量加入 主队vs客队, 加大搜索可见"。

**我初版的错误**: 一度把"含场次编号"写成"本批最稳的标题信号"(聚合 CTR 8.1% vs 7.0%)。
加上 bootstrap 后 **p=0.055, 不显著**, 已降级为"不成立(待验证)"。
**聚合 CTR 的大小差 ≠ 真信号** —— 这是本次自己踩的坑。

**诚实结论**: 后台导出**没有搜索来源字段**, 展现量是"推荐+搜索+关注"的合计,
所以 **无法用本数据验证搜索收益**。能验证的只有"**加 vs 在推荐侧没有代价**"(CTR 差 −0.03pp, p=0.991)。

**顺带修掉一个自己的错误**: 起初算出"含 vs 展现更低 1,929"。按月份分层后**反转**:

| 月份 | 含vs − 不含vs 展现中位差 |
|---|---|
| 2026-05 | **+1,606** |
| 2026-07 | −86 |
| 2026-08 | **+2,884** |
| 2026-09 | **+3,224** |

原始的负差是**月份构成造成的**(9 月稿展现高、恰好多无 vs)—— **正是我们批判旧复盘时的同一个辛普森悖论**。

**规则可行性(不能让规则自相矛盾)**: "必须含队名对位" + "≤36字" 直接**插入**会冲突(4 例中 3 例 39~42 字);
改成**替换**(把模糊描述换成队名)则 4 例全部 25~34 字。净字数不增, 因为旧标题把 7~10 字
浪费在"客场垫底当热门"这种搜索不认的描述上。

**已落地的改动**
1. `02_工具/check_md_release.py`: 新增 `has_team_vs()` —— 标题缺「主队vs客队」直接判**不通过**;
   含**假阳性黑名单**(模型/市场/机构/数据…), 避免 `模型vs市场` 这种蒙混(1 篇历史稿命中)。
   同时修正标题长度注释: 36 字上限**无害但也无收益**(>36 vs ≤30 p=0.575), 保留只为防截断。
2. `01_工作流SOP/workflow.md`: §零·五 整段重写(形态/时段/标题/赛事四项), 另修 3 处遗留的"≤30 字"。
3. 模板: **`周X 编号 联赛 主队vs客队：一个反差点`**, 反差点 ≤12 字, **超长先砍反差点, 不砍队名**。

**实例**(周五011+008 头条稿):
- 原标题 `周五011+008:布伦特福德10场不败受让,拜仁让三球未开售`(31字) → ❌ 无队名对位
- 正文里其实**已有** `布伦特福德(主)vs 切尔西 — 周五011` —— 只是没提到标题
- 改为 `周五011 布伦特福德vs切尔西：10场不败受让,拜仁让三球`(30字) → ✅ 通过

**用户确认的判定口径**: 标题里**只要有任意一处真实的队名对位就通过**(多场稿只需写主打那一场)。

**这次为了对上这个口径, 抓到并修掉两个 bug —— 记录一下, 因为两个都是"看数字才发现"的:**

1. **只查第一处 → 不符合"任意一处"**
   初版用 `RE_TEAM_VS.search()` 只取**最左边**那一处对位; 若它恰是假阳性(`模型vs市场`),
   后面的真队名(`罗马vs国米`)就被连带否掉。改为逐个 `vs` 独立扫描后修复。
   **回归计数是唯一暴露它的手段** —— 修复后通过数从 142 掉到 138, 而新实现是旧实现的超集, 减少就是 bug。

2. **漏了 vs 两侧的空格(靠上一条的计数异常才查到)**
   新实现逐字符取连续串, 遇到空格就断 → `阿根廷 vs 佛得角`、`拜仁慕尼黑 VS 巴黎圣日耳曼`
   左侧取到 **0 字**被误杀(旧正则里有 `\s*` 所以没暴露)。
   **教训: 重写一个已经能跑的匹配逻辑时, 必须保留旧实现做差分回归, 光看"单元测试全过"不够** ——
   6 条手工用例全过, 但真实数据上掉了 4 篇。顺带把稿件惯例的 `(主)`/`（主）` 注解也纳入预处理
   (否则 `布伦特福德(主)vs 切尔西` 左侧取到的是"主")。
   修复后回归 **142/262, 与旧实现逐篇一致(双向 0 差异)**。
